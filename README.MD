# Hospital API — Tarea 013

API REST de usuarios desarrollada con **Node.js, Express 5, PostgreSQL 16.15 y Sequelize 6**, como parte de la Clase 7 de Node.js (Kopius — The Academy).

Incluye el CRUD de usuarios de la **Tarea 013** y la ampliación propuesta en el **Desafío 7.6: contraseñas y roles**.

> **Alcance:** aunque el repositorio se llama `hospital-api`, por ahora trabaja con usuarios. No incluye todavía pacientes, turnos ni hospitales.
>
> **Uso educativo:** la autorización por el header `x-user-role` es una **simulación insegura** exigida por la práctica. No es apta para producción ni debe exponerse públicamente con datos reales.

## Tecnologías

- **Node.js 24 / Express 5:** servidor HTTP y rutas REST.
- **PostgreSQL 16.15 / Docker Compose:** base relacional y persistencia local.
- **Sequelize 6 / pg / pg-hstore:** ORM y conexión a PostgreSQL.
- **Yup:** validación, normalización y DTOs de entrada y salida.
- **bcrypt:** hash y verificación de contraseñas.
- **dotenv / cors:** variables de entorno y configuración CORS.
- **pgAdmin 4 (opcional):** cliente gráfico de PostgreSQL.
- **REST Client de VS Code (opcional):** ejecución de peticiones HTTP desde `api.http`.

## Requisitos

- Node.js (recomendado: **24**, versión usada durante la práctica) y npm.
- Docker Desktop en ejecución.
- pgAdmin 4 u otro cliente PostgreSQL, o acceso a `psql` mediante Docker.

### 2. Crear el `.env`

```powershell
Copy-Item .env.example .env
```

Ejemplo de configuración local:

```dotenv
PORT=3000

DB_HOST=127.0.0.1
DB_PORT=5433

DB_USER=postgres
```

- `DB_PASSWORD` debe coincidir con la contraseña configurada **dentro de PostgreSQL**, no solo con una nueva contraseña escrita en el `.env`.
- `.env` contiene secretos: **no subirlo a Git**. El `.env.example` sí se versiona, con una contraseña ficticia.
- Se utiliza **5433 en Windows** porque ya había otra instancia local de PostgreSQL utilizando `5432`.

### 3. Levantar PostgreSQL

Desde la raíz del proyecto:

```powershell
docker compose up -d --wait
docker compose ps
```

Configuración relevante de `docker-compose.yaml`:

```yaml
services:
  db:
    image: postgres:16.15
    container_name: nodepgdb
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: ${DB_NAME}
    ports:
      - "5433:5432"
    volumes:
      - ./postgres:/var/lib/postgresql/data
```

| Servicio | Puerto |
| --- | --- |
| PostgreSQL visto desde Windows / pgAdmin / Node.js | `5433` |
| PostgreSQL dentro del contenedor | `5432` |
| API Express | `3000` |

El directorio `postgres/` almacena los datos. `docker compose down` detiene y elimina el contenedor, **sin borrar esa carpeta**.

### 4. Preparar la base de datos

En pgAdmin, registrá el servidor con **host `127.0.0.1`**, puerto **`5433`**, usuario **`postgres`**, la contraseña de PostgreSQL y base **`nodepgdb`**. Abrí el **Query Tool** de `nodepgdb`.

**Para una instalación nueva (tabla todavía inexistente)**, ejecutá este SQL **una sola vez**:

```sql
CREATE TYPE user_role AS ENUM ('ROLE_USER', 'ROLE_ADMIN');

CREATE TABLE users (
  id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name VARCHAR(120) NOT NULL,
  email VARCHAR(255) NOT NULL UNIQUE,
  password VARCHAR(255) NOT NULL,
  role user_role NOT NULL DEFAULT 'ROLE_USER',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

La columna `password` guarda **un hash de bcrypt**, nunca la contraseña en texto plano. El valor inicial del rol es `ROLE_USER`.

**Si ya tenías la tabla de la Tarea 013 sin `password` ni `role`**, no ejecutes el `CREATE TABLE` anterior: seguí el apartado siguiente.

### Crear un usuario

```http
POST http://localhost:3000/api/users
Content-Type: application/json

{
  "name": "Ada Lovelace",
  "email": "ADA@Example.com",
  "password": "ClaveDePrueba123!"
}
```

Ejemplo de respuesta `201 Created` (el ID puede variar):

```json
{
  "data": {
    "id": 1,
    "name": "Ada Lovelace",
    "email": "ada@example.com",
    "role": "ROLE_USER"
  }
}
```

Yup normaliza el email, valida los campos permitidos y exige una contraseña de al menos 8 caracteres. bcrypt genera el hash antes de guardar; **la contraseña y el hash nunca forman parte de la respuesta pública**. El DTO de creación no permite enviar `role`.

### Login

```http
POST http://localhost:3000/api/auth/login
Content-Type: application/json

{
  "email": "ada@example.com",
  "password": "ClaveDePrueba123!"
}
```

Respuesta esperada para credenciales correctas: `200 OK` y `data` con `id`, `name`, `email`, `role`. Para email inexistente o contraseña incorrecta, se devuelve **el mismo error**:

```json
{
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "Invalid credentials"
  }
}
```

Estado: **401 Unauthorized**. El login de este ejercicio **no emite JWT, cookie ni sesión**; solamente verifica las credenciales.

### Actualizar contraseña

```http
PATCH http://localhost:3000/api/users/1
Content-Type: application/json

{
  "password": "NuevaClave456!"
}
```

El controller vuelve a ejecutar `bcrypt.hash` antes de guardar. La contraseña nueva debe permitir el login y la anterior debe fallar. **Este endpoint no verifica quién solicita el cambio:** es parte de la práctica, no un diseño seguro de producción.

### Cambiar el rol de un usuario

```http
PATCH http://localhost:3000/api/users/1/role
Content-Type: application/json
x-user-role: ROLE_ADMIN

{
  "role": "ROLE_ADMIN"
}
```

Valores posibles: `ROLE_USER`, `ROLE_ADMIN`. Si falta `x-user-role` o vale `ROLE_USER`, el middleware responde `403 FORBIDDEN`. Si el body contiene `"role": "ADMIN"`, Yup responde `400 VALIDATION_ERROR`.

> **Advertencia de seguridad:** `x-user-role` es un encabezado **controlado por el cliente**, y cualquiera puede enviar `ROLE_ADMIN`. Es solo una simulación para aprender middleware de autorización. Una API real debe verificar la identidad y obtener el rol de una sesión o token validado por el servidor.

## DTOs, validaciones y seguridad de datos

- **`createUserDto`:** requiere `name`, `email`, `password`; rechaza claves desconocidas como `role` o `password_hash`.
- **`updateUserDto`:** permite actualizar uno o más de `name`, `email`, `password`; rechaza el objeto vacío.
- **`assignRoleDto`:** acepta solo los roles declarados en el ENUM.
- **`loginDto`:** valida el email y la contraseña enviados al login.
- **`toUserResponse`:** expone exclusivamente `id`, `name`, `email`, `role`.
- **Sequelize / PostgreSQL:** aplican validaciones de modelo, `NOT NULL`, `UNIQUE` y el ENUM nativo `user_role`.
- **bcrypt:** genera hashes con 12 rondas de salt en este desafío. No registrar contraseñas ni hashes en logs.

> bcrypt limita la entrada efectiva a **72 bytes**. Si tu implementación usa la validación adicional de bytes, mantenela alineada con el DTO; para producción conviene revisar cuidadosamente la política de longitud y no modificar contraseñas silenciosamente.

1. Detené Node y PostgreSQL (`docker compose down`).

3. Volvé a levantar PostgreSQL y reiniciá la API.

## Problemas frecuentes

| Mensaje / síntoma | Qué revisar |
| --- | --- |
| `password authentication failed` desde pgAdmin | Conectar al puerto `5433` y usar la contraseña real del usuario `postgres`. Cambiar el `.env` no modifica una base ya inicializada. |
| `relation "users" does not exist` | Crear o migrar la tabla en **`nodepgdb`** y verificar `DB_NAME` / `DB_PORT`. |
| `column "password" does not exist` | Falta la migración del desafío a la tabla existente. |
| `type "user_role" does not exist` | Falta ejecutar `CREATE TYPE user_role ...` antes de agregar la columna. |
| `column "createdAt" does not exist` | Verificar `underscored: true`. |
| `Missing parameter name ... :/id` | Corregir rutas: `/:id` (no `:/id`). |
| `GET /api/users/search` devuelve `INVALID_ID` | Declarar `/search` antes de `/:id`. |
| `port is already allocated` | Evitar el conflicto local manteniendo `5433:5432` y `DB_PORT=5433`. |
| `ECONNREFUSED` | Ejecutar `docker compose ps` y verificar que Docker esté arriba. |
| `password` aparece en la respuesta | Usar `toUserResponse`, nunca devolver el modelo Sequelize sin filtrar. |
| `403` al cambiar roles | Es esperado sin el header de prueba `x-user-role: ROLE_ADMIN`. |

# Clase 9 — Tarea 015: Autenticación y autorización con JWT

## Descripción

En esta etapa se amplió **Hospital API**, desarrollada durante las Clases 7 y 8 de Kopius Academy, para incorporar autenticación y autorización mediante **JSON Web Tokens (JWT)**.

La API permite identificar usuarios mediante correo electrónico y contraseña, emitir tokens de acceso y restringir las operaciones sobre los recursos hospitalarios según el rol del usuario autenticado.

También se incorporaron medidas adicionales de seguridad, documentación OpenAPI con autenticación Bearer y pruebas de integración.

## Tecnologías utilizadas

- Node.js y JavaScript ES Modules
- Express
- PostgreSQL y Sequelize
- bcrypt para hashing y verificación de contraseñas
- jsonwebtoken para generación y validación de JWT
- Helmet para cabeceras HTTP de seguridad
- express-rate-limit para limitar intentos de login
- Swagger UI y OpenAPI
- Postman para pruebas HTTP
- Supertest y node:test para tests automatizados
- Docker Compose para PostgreSQL

## Autenticación mediante JWT

### POST /api/auth/login

Permite autenticar un usuario mediante sus credenciales.

**Request:**

```http
POST /api/auth/login
Content-Type: application/json
```

```json
{
  "email": "usuario@hospital.local",
  "password": "PASSWORD_DEL_USUARIO"
}
```

**Respuesta exitosa — HTTP 200:**

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIs...",
  "tokenType": "Bearer",
  "expiresIn": 900
}
```

El Access Token:

- Se firma mediante HS256.
- Tiene una duración de 15 minutos.
- Contiene los claims `sub`, `role`, `iss`, `aud`, `iat` y `exp`.
- No contiene contraseñas ni información clínica.
- Debe enviarse en el header `Authorization` para acceder a recursos protegidos.

Las credenciales incorrectas devuelven `401 INVALID_CREDENTIALS`, sin revelar si el correo electrónico existe.

Las cuentas inactivas tampoco pueden iniciar sesión.

### GET /api/auth/me

Devuelve el perfil público del usuario autenticado.

**Request:**

```http
GET /api/auth/me
Authorization: Bearer ACCESS_TOKEN
```

**Respuesta exitosa — HTTP 200:**

```json
{
  "data": {
    "id": 1,
    "name": "Usuario de prueba",
    "email": "usuario@hospital.local",
    "role": "ADMIN"
  }
}
```

El perfil se obtiene desde PostgreSQL después de verificar el JWT.

La respuesta utiliza un DTO público, por lo que no expone el hash de contraseña.

## Usuarios y roles

El modelo `User` dispone de:

| Campo | Descripción |
|---|---|
| id | Identificador del usuario |
| name | Nombre |
| email | Correo electrónico único |
| password | Hash bcrypt de la contraseña |
| role | Rol de autorización |
| isActive | Estado de la cuenta |

Los roles utilizados en esta versión son:

- `ADMIN`
- `DOCTOR`
- `RECEPTIONIST`

Los roles anteriores de la Clase 7 (`ROLE_USER` y `ROLE_ADMIN`) fueron reemplazados en las reglas de negocio por los nuevos roles.

La asignación y modificación de roles está restringida a usuarios administradores.

## Autorización de recursos

Se implementaron dos middlewares principales:

**authenticate**

Verifica que la petición tenga un JWT válido, comprueba su firma, expiración, emisor y audiencia, y recupera el usuario actual desde PostgreSQL.

**authorize**

Comprueba que el usuario autenticado tenga uno de los roles autorizados para ejecutar la operación solicitada.

### Matriz de permisos

| Recurso | ADMIN | DOCTOR | RECEPTIONIST |
|---|---|---|---|
| Users | CRUD y roles | Sin acceso | Sin acceso |
| Patients | CRUD completo | Lectura | Lectura, creación y actualización |
| Doctors | CRUD completo | Lectura | Lectura |
| Nurses | CRUD completo | Lectura | Lectura |
| Specialties | Lectura | Lectura | Lectura |
| Appointments | CRUD completo | Lectura, creación y actualización | Lectura, creación y actualización |

Las operaciones de eliminación quedan reservadas al rol ADMIN cuando corresponda.

Esta matriz implementa permisos por función y rol. No incorpora todavía restricciones de acceso por pertenencia a un paciente o médico específico.

### Respuestas de autorización

**401 Unauthorized**

Se utiliza cuando no existe una autenticación válida.

Ejemplos:

- No se envía un Access Token.
- El token tiene una firma inválida.
- El token está vencido.
- El usuario ya no existe o está inactivo.

**403 Forbidden**

Se utiliza cuando el usuario está autenticado, pero no posee los permisos necesarios.

Por ejemplo, cuando un usuario `RECEPTIONIST` intenta eliminar un paciente.

El antiguo mecanismo de autorización mediante `x-user-role` fue eliminado. Los permisos se obtienen exclusivamente de la identidad autenticada y su rol vigente.

## Medidas adicionales de seguridad

### Hashing de contraseñas

Las contraseñas se almacenan mediante bcrypt. Nunca se devuelve el campo `password` en las respuestas de la API.

### Helmet

Se incorporó Helmet para establecer cabeceras HTTP de seguridad.

Swagger UI utiliza un archivo JavaScript externo (`docs/swagger-init.js`) para funcionar con la política Content Security Policy.

### Rate limiting

El endpoint `POST /api/auth/login` cuenta con un limitador de intentos.

La configuración implementada permite hasta 10 intentos fallidos durante una ventana de 15 minutos por IP, utilizando almacenamiento en memoria.

Cuando se supera el límite, la API devuelve:

**HTTP 429 Too Many Requests**

```json
{
  "error": {
    "code": "TOO_MANY_REQUESTS",
    "message": "Too many login attempts, please try again later"
  }
}
```

### Validación y DTOs

Los cuerpos de entrada se validan mediante Yup.

Los DTOs de salida evitan exponer propiedades internas y credenciales.

El servidor limita el tamaño del cuerpo JSON recibido.

## Configuración de JWT

La aplicación utiliza la variable de entorno `JWT_SECRET`.

Esta variable debe contener un secreto aleatorio de alta entropía y no debe almacenarse en el repositorio.

Ejemplo de configuración local:

```dotenv
NODE_ENV=development
PORT=3000
CORS_ORIGIN=http://localhost:5173

DB_HOST=127.0.0.1
DB_PORT=5433
DB_NAME=nodepgdb
DB_USER=postgres
DB_PASSWORD=REEMPLAZAR_CON_PASSWORD_LOCAL

JWT_SECRET=REEMPLAZAR_CON_SECRETO_ALEATORIO
```

Para generar un secreto desde Node.js:

```powershell
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Los archivos `.env` y `.env.test` contienen configuraciones privadas y no deben subirse a Git.

Se deben utilizar secretos distintos para desarrollo y pruebas.

## Documentación Swagger y OpenAPI

La especificación se encuentra en:

`docs/openapi.yaml`

http://localhost:3000/docs

Swagger UI permite autenticar las peticiones mediante el esquema `bearerAuth`.

### Uso de Swagger con JWT

1. Iniciar la API.
2. Abrir `/docs`.
3. Ejecutar `POST /api/auth/login`.
4. Copiar `accessToken` de la respuesta.
5. Presionar **Authorize**.
6. Pegar el token, sin el prefijo `Bearer`.
7. Ejecutar los endpoints protegidos.

El contrato documenta las respuestas de autenticación y autorización, incluyendo los estados `401`, `403` y `429` cuando corresponden.

Para validar OpenAPI:

```powershell
npx @redocly/cli lint docs/openapi.yaml
```
